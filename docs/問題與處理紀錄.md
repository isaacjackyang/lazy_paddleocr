## 問題摘要

修復前主要觀察到兩個核心問題：

1. 使用 CPU 路徑時，可能出現 oneDNN / PIR 相關錯誤，代表推理過程在 Paddle 的 CPU 加速路徑失敗。
2. V5 的 TXT 輸出為空白，不是模型完全沒跑，而是啟動器讀錯了新版 PaddleOCR 的輸出 JSON 結構。

使用者提供的代表性錯誤訊息：

```text
[ERROR]
NotImplementedError: (Unimplemented) ConvertPirAttribute2RuntimeAttribute not support [pir::ArrayAttribute<pir::DoubleAttribute>]  (at ..\paddle\fluid\framework\new_executor\instruction\onednn\onednn_instruction.cc:118)
```

## 修復前已確認事實

### 1. CPU / MKLDNN 行為原本沒有被明確控制

修復前分析時，`run_ocr_launcher.py` 建立推理物件是直接呼叫：

- `PaddleOCR(...)`
- `PPStructureV3()`

當時沒有看到明確傳入：

- `device`
- `enable_mkldnn`
- `cpu_threads`

而 `paddleocr 3.4.0` 的 CPU 預設值傾向會啟用 MKLDNN / oneDNN，因此和 `onednn_instruction.cc` 類錯誤高度吻合。

### 2. V5 TXT 空白的直接原因已定位

修復前的後處理邏輯假設 OCR JSON 長這樣：

```json
{
  "rec_texts": [...],
  "rec_scores": [...]
}
```

但在目前安裝的 `paddleocr 3.4.0` 實測中，結果實際更接近：

```json
{
  "res": {
    "rec_texts": [...],
    "rec_scores": [...],
    "rec_polys": [...]
  }
}
```

也就是真正的文字結果包在 `res` 底下，而不是直接放在最外層。這會讓原本的：

- `filter_ocr_payload(...)`
- `results_to_text(...)`

抓不到真正文字，最後造成 TXT 空白。

### 3. 這不是單純模型失效

實測 `PaddleOCR(...).predict(...)` 有正常回傳資料，且 `json["res"]` 底下確實存在 `rec_texts`。

因此問題不在模型本身沒有跑，而是在啟動器後處理沒有跟上新版輸出格式。

### 4. 關於「V3 TXT 有問題」

當前啟動器對外模式其實是：

- `PP-OCRv5`
- `PP-StructureV3`

不是獨立的 `PP-OCRv3` 模式。

如果使用者提到的「V3」其實是：

- `PP-StructureV3`，那問題多半和深層 JSON 結構、抽取規則或 CPU 推理路徑有關。
- `PP-OCRv3`，則目前啟動器仍沒有提供正式切換選項。

## 原因判斷

### A. oneDNN / PIR 錯誤

高機率原因：

- 本機安裝版落到 CPU 推理
- MKLDNN / oneDNN 被啟用
- Paddle 3.x 在 oneDNN + PIR 的某些模型或屬性組合上出現不相容

雖然目前沒有在這台機器上穩定重現完全相同的錯誤訊息，但從：

- 錯誤堆疊位置
- PaddleOCR 預設行為
- 修復前啟動器缺少顯式 CPU / MKLDNN 控制

可以合理判定這是同一路徑上的問題。

### B. TXT 空白

直接原因已明確確認：

- 程式讀錯 JSON 結構
- 真正的 `rec_texts` 在 `payload["res"]`
- 原本程式卻在最外層找 `payload["rec_texts"]`

## 目前修復結果總結

就目前程式可確認的結果來看，已完成的核心修復有：

1. 修正 PaddleOCR 3.4.0 JSON 結構變動造成的 TXT 空白問題。

6. 補上遞迴掃描時的排除規則，避免掃進 `.venv`、暫存輸出與已生成檔案。
7. 補強安裝器的環境驗證、依賴修復、手動修復清單與 Python / venv 重用邏輯。

保守註記仍然存在，但重點已從「功能尚未補上」變成「仍需真實資料持續驗證」：

## 問題與解決方式整理

### 1. V5 TXT 空白

#### 原本問題

- 程式假設 OCR 結果是平面 JSON。
- 新版 PaddleOCR 把主要內容包在 `res` 底下，造成最終 TXT 抽不到文字。

#### 目前修復方式

- 新增 `normalize_json_attr(...)`，會先把 `res` 包裝層解開。
- `filter_ocr_payload(...)` 改吃標準化後的 payload。
- 圖片與 PDF 路徑都統一走這個 normalize 流程。

#### 與原本程式的差異

- 原本：直接把最外層當成最終 OCR 結果。
- 現在：先標準化 JSON 結構，再進行信心分數篩選與文字輸出。

#### 修復效果判定

- 這是目前最明確、最直接已落地的修正。
- 依現有程式結構判斷，V5 TXT 空白問題已被正面處理。

### 2. PP-StructureV3 / 深層結構結果抽不到文字

#### 原本問題

- 不同模式的輸出結構深度不同。
- 如果只讀固定欄位，`PP-StructureV3` 這類巢狀結果很容易漏字。

#### 目前修復方式

- 先透過 `extract_structure_texts(...)` 優先讀取 structure result 的 markdown / plain-text 輸出。
- 新增 `normalize_structure_text(...)`，會處理：
  - HTML tag 清理
  - table / cell 換行與 tab 分隔
  - 空白與段落整理
- 若 markdown 路徑拿不到內容，才退回 `extract_texts_deep(...)` 深層遞迴搜尋：
  - `markdown_texts`
  - `rec_texts`
  - `text`
  - `markdown`
  - `content`
- 再透過 `dedupe_keep_order(...)` 去重並保留順序。
- `results_to_text(...)` 在 structure 模式下，統一讀取 `_extracted_texts`。

#### 與原本程式的差異

- 原本：較偏單一路徑抽值，抽到的內容也較容易把結構與原始 HTML 混在一起。
- 現在：先走較高品質的 markdown / plain-text 抽取，再用深層遞迴做保底。

#### 修復效果判定

- 這代表目前程式不只修掉 V5 TXT 空白，也同步補上 structure 類輸出的文字整併與可讀性改善。

### 3. CPU / GPU 裝置控制不足

#### 原本問題

- 啟動器沒有明確控制 `device`。
- 當 GPU wheel 與實機 GPU 架構不相容，或使用者想強制走 CPU 時，流程不夠明確。

#### 目前修復方式

- `run_ocr_launcher.py` 新增 `--device auto|cpu|gpu`
- `start_ocr_launcher.ps1` 新增 `-Device Auto|CPU|GPU`
- 新增 `force_cpu_runtime()`，會設定 `CUDA_VISIBLE_DEVICES=""`
- 新增 `is_gpu_init_error(...)` 與 `create_mode_pipeline(...)`
- `Auto` 模式下若 GPU 初始化失敗，會自動回退到 CPU

#### 與原本程式的差異

- 原本：裝置選擇隱含在函式庫預設裡。
- 現在：裝置選擇成為正式參數，並且有明確 fallback 流程。

#### 修復效果判定

- 這可以有效改善 GPU 初始化失敗就整體不能跑的問題。
- 原生 CPU 的 oneDNN / MKLDNN 風險已在後續版本中再補上更直接的顯式修法與 retry。

### 4. oneDNN / PIR 問題目前的處理狀態

#### 本次已落地修法

- 在原生 CPU 模式建立 pipeline 時，會明確帶入 `enable_mkldnn=False`。
- `force_cpu_runtime(...)` 仍會同時設定：
  - `PADDLE_PDX_ENABLE_MKLDNN_BYDEFAULT=False`
  - `FLAGS_use_mkldnn=0`
- 新增 oneDNN / PIR 錯誤辨識關鍵字，例如：
  - `onednn`
  - `mkldnn`
  - `pir`
  - `convertpirattribute2runtimeattribute`
- 新增 `predict_with_runtime_retry(...)` 與 `rebuild_runtime_with_cpu_retry(...)`
  - 一旦命中 oneDNN / PIR runtime 錯誤
  - 會重建全新的 CPU pipeline
  - 並在 MKLDNN disabled 狀態下自動重試一次

#### 目前掃描到的現況

- 原生啟動器已不再只是「降低風險」，而是已有明確的顯式修法。
- Docker 啟動器仍另外加入 `PADDLE_PDX_ENABLE_MKLDNN_BYDEFAULT=False`，等於容器路線上多一層固定保護。

#### 研究結論

- 如果遇到的是 GPU 初始化或 GPU 相容性問題，現在版本已有明顯改善。
- 如果遇到的是原生 CPU oneDNN / PIR 問題，現在版本已具備顯式停用 MKLDNN 與自動 retry 的正式修補。
- 目前剩下的主要不確定性，不是「有沒有修」，而是「是否還存在尚未覆蓋到的罕見錯誤型態」。

### 5. 遞迴掃描容易掃到不該處理的資料夾與已生成輸出

#### 原本問題

- 可能把 `.venv`、`__pycache__`、已產出的 `.txt/.json`、PDF 轉圖中繼檔再掃一次。
- 這會造成結果污染或重複處理。

#### 目前修復方式

- 新增 `EXCLUDED_DIR_NAMES`，排除：
  - `.venv`
  - `venv`
  - `__pycache__`
  - `.git`
  - `_pdf_pages`
  - `node_modules`
- 新增 `should_skip_generated_file(...)`，避免重新掃描：
  - `.ppocrv5.txt`
  - `.ppocrv5.json`
  - `.ppstructurev3.txt`
  - `.ppstructurev3.json`
  - knowledgebase 輸出檔

#### 修復效果判定

- 這屬於穩定度提升，不只是功能新增。
- 對批次掃描尤其重要。

### 6. 安裝器從一次性安裝補強成可驗證、可修復、可回退

#### 原本問題

安裝流程較容易遇到：

- `.venv` 與系統 Python 版本不一致卻仍被重用
- PaddlePaddle GPU wheel 裝好但實際 GPU 驗證失敗
- `PP-StructureV3` 依賴不完整
- 安裝中斷後缺少清楚的手動修復步驟

#### 目前修復方式

- 新增 `-StrictVenvPythonMatch`
- `Test-VenvReusable` 會檢查 venv 與當前 Python 的相容性
- 安裝器會設定 `PADDLE_PDX_DISABLE_MODEL_SOURCE_CHECK=True`
- `Ensure-PaddleInstalled` 會先嘗試 GPU，失敗自動 fallback 到 CPU
- `Ensure-StructureDependenciesInstalled` 會驗證 `PP-StructureV3` 是否真的可用，不行時補裝 `paddlex[ocr]==3.4.2`
- `Verify-Installation` 不只檢查 import，還會實際建立 `PaddleOCR(...)`、`PPStructureV3()` 與執行 `paddle.utils.run_check()`
- 安裝失敗或 structure 尚未就緒時，會輸出 `install_manual_recovery.ps1`

#### 修復效果判定

- 這一部分是本次成熟度提升最大的區塊之一。
- 對跨電腦搬移與重複部署都很有幫助。

### 7. 啟動器操作流程變得可控

#### 目前新增或補強的操作面差異

- 預設改成遞迴掃描，但可用 `-NoRecursive` 關閉
- 啟動前會顯示目前設定，包含：
  - Python 路徑
  - 啟動器路徑
  - 遞迴狀態
  - Device
  - PDF DPI
  - 圖片 / PDF 副檔名
- 互動式流程會詢問：
  - 掃描類型
  - OCR 模式
  - 信心分數門檻
  - 輸出格式是 `TXT only` 或 `TXT + JSON`

#### 修復效果判定

- 這些不只是介面調整，也是在避免使用者因為預設不透明而誤判結果。

## 後續處理紀錄

本節將本串對話中的後續處理，依主題整理，避免原本多個「追加紀錄 / 補充紀錄 / 新增補記」章節重複描述。

### A. 安裝與環境

#### 1. Windows PowerShell 5.1 安裝說明與腳本化

- 已整理 PowerShell 5.1 下安裝 PaddleX、PP-StructureV3、PP-OCRv5 的正確順序：
  - Python
  - virtual environment
  - PaddlePaddle
  - PaddleX
  - 第一次執行 pipeline 時自動下載模型
- 已提供可直接複製貼上的 PowerShell 安裝腳本版本。

#### 2. CPU / GPU 雙環境安裝腳本

- 使用者要求 CPU 與 GPU 版本都要能保留。
- 判斷後採用雙 venv 架構，而不是在同一個環境中互相覆蓋：
  - `.venv-cpu`
  - `.venv-gpu`

  - `tools\install_paddleocr.ps1`
- 此腳本定位為：
  - 精簡版
  - 雙環境安裝
  - 不含完整 launcher 整合與 manual recovery

#### 3. `install_paddleocr.ps1` 與 `install_paddle_ocr_suite.ps1` 差異

- `install_paddleocr.ps1`
  - 目標是快速把 CPU / GPU 兩套環境都準備好
  - 安裝內容偏精簡
  - 不處理啟動器整合與手動修復清單
- `install_paddle_ocr_suite.ps1`
  - 目標是把單一可用環境安裝到可驗證、可修復、可啟動
  - 功能較完整
  - 但不是同時保留 CPU / GPU 兩套環境

#### 4. `.venv` 跨電腦重用不穩

- 已確認 Windows `.venv` 不是可攜式成品。
- 若整包專案連 `.venv` 複製到另一台電腦，常見問題包括：
  - `ModuleNotFoundError: No module named 'paddle'`
  - `PP-StructureV3 dependency install failed validation`
- 已在 `install_paddle_ocr_suite.ps1` 補強：
  - `pyvenv.cfg` 的 `home` / `executable` 檢查
  - Python 白名單偵測
  - OCR / Structure runtime readiness 驗證
- 結論：
  - 模型快取可搬
  - `.venv` 不建議直接跨機器搬用

#### 5. GPU 安裝卡住與手動修復機制

- 已針對 GPU wheel 安裝長時間卡住補上總超時機制。
- 超時後：
  - 會中止 GPU 安裝
  - 自動退回 CPU 路徑
- 若安裝失敗，現在會產生：
  - `install_manual_recovery.ps1`
  - `Manual recovery checklist`

### B. OCR 輸出與執行行為

#### 1. `TXT only` 仍輸出 JSON

- 已修正 `run_ocr_launcher.py` 的輸出模式邏輯。
- 現在 `TXT only` 時：
  - 只輸出 `.txt`
  - 不再輸出 `.json`
  - 不再輸出 `knowledgebase.jsonl`
- 舊 JSON 也會視情況清除。

#### 2. 掃描類型需要可選 picture / PDF / picture+PDF

- 已在 `run_ocr_launcher.py` 增加互動選單。
- 對應行為：
  - `picture`：只掃 `JPG / JPEG / PNG / BMP / WEBP`
  - `PDF`：只掃 `.pdf`
